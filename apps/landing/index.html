How it routes

01

Call one endpoint

Send a payment or a message the same way, with an Idempotency-Key so a retried request can never charge or send twice.

POST /v1/api/gateway/payment
Idempotency-Key: 8f14e-...

{
  "appId": "afribook",
  "amount": 2500,
  "currency": "USD",
  "paymentMethod": "card"
}
02

The engine picks the rail

Nine payment rails, five messaging rails. The routing engine checks live health and picks one; if that rail errors, it tries the next before your request ever fails.

03

One verified webhook back

Every provider webhook is HMAC-verified on arrival and lands in Postgres first — if the queue backend is down, it waits there and replays the moment it's back. Nothing drops at the door.

Built for the failure cases, not just the happy path

Idempotent by default

The same key and payload always return the same result. A reused key with a different payload gets a 409, not a silent double charge.

Durable by design

Inbound webhooks land in Postgres before anything else happens. If the job queue's backend is unreachable, events wait safely and drain the moment it recovers.

Backpressure, not collapse

Every queue has a configurable depth cap. Once it's hit, new jobs are rejected immediately with a clear error — never queued silently until they die downstream.

Tenant isolation

Every request is scoped to your application and tenant at the query level. One customer's records never surface in another's lookup.

Pay for what moves, not for seats

Questions builders actually ask

What happens when a provider goes down?

The routing engine detects the failure and tries the next healthy rail before your request times out. If a webhook can't be delivered, it's retried from a durable queue instead of being lost.

Do you ever hold our funds?

No. BIS routes requests to the payment and messaging accounts you connect — it isn't a custodian. Money and messages move directly between your customer and your own provider accounts.

Which African corridors do you support?

Mobile money and card rails across multiple African markets through pawaPay, PayChangu, and Flutterwave, alongside the global card and bank rails.

Is this only for payments?

No — the same gateway routes SMS, WhatsApp, and email through Twilio, Infobip, SignalHouse, FutureSMS, and email, with STOP/HELP/YES/NO compliance keywords already handled.

How do I try it?

Create a free account, generate a sandbox API key, and send your first request — no card required to start.
